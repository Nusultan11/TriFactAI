# RAG pipeline TriFact AI

## Когда применять

- Сборка и отладка потока `POST /v1/ask` (архитектура §6.2), промпта, сборки контекста, политики отказа.
- Разбор конкретного плохого ответа или падения e2e-метрики.
- Этап 9: end-to-end eval и ablation.

Модель генерации и её дообучение — `trifact-llm-finetuning`. Поиск — `trifact-retrieval`. NLI-проверка — `trifact-verification`.

## Принципы

1. Каждая стадия меряется отдельно и в составе цепочки. Сквозная метрика без постадийных не говорит, что чинить.
2. Сначала простейшая цепочка: гибрид → reranker → top-k → LLM → NLI. Компонент (переписывание запроса, HyDE, многошаговый поиск) добавляется только при выигрыше в ablation с CI и при допустимой латентности.
3. Один и тот же промпт и шаблон чата при SFT, eval и сервинге (ADR-0012).

## Сборка контекста

- **Дедупликация:** почти одинаковые чанки (зеркала, шаблонные статьи) схлопываются, оставляется лучший по reranker.
- **Склейка:** смежные по смещениям чанки одного документа объединяются в один пассаж. Это сохраняет связность и экономит заголовки.
- **Порядок:** по убыванию оценки reranker, сильнейшие в начале. Модели хуже используют середину длинного контекста («lost in the middle»), поэтому k держится малым, а не «сколько влезет».
- **Бюджет в токенах генератора по языку.** kk дороже по токенам (models.md §6.2), поэтому при одинаковом k kk-контекст длиннее. Считать токенизатором Qwen3.5 и резать по бюджету, а не по числу чанков.
- **Шапка пассажа:** номер `[n]` (переводится в `chunk_id` после генерации — короче, меньше обрезаний), заголовок документа, раздел, страница, язык.

## Промпт и поведение модели

- Язык ответа задаётся явно. Межъязыковые доказательства переводятся без добавления фактов. Язык ответа проверяется langid после генерации.
- Ссылка после каждого факта. Допустимы только переданные номера. Невалидная ссылка — ошибка формата, она считается метрикой.
- Отказ — точная фраза на языке ответа (`grounded_answer.md`). Это делает refusal детектируемым строкой.
- Режим non-thinking, низкая температура, стоп-последовательности. Длина ответа ограничена.
- **Противоречивые источники:** модель показывает обе версии со своими ссылками и не выбирает одну молча. Противоречие фиксирует NLI на стадии проверки.

## Prompt injection

Пользовательские документы — недоверенный ввод. Текст пассажа может содержать «инструкции».

- Пассажи изолируются разделителями (spotlighting), правило в промпте: в доказательствах — данные, не команды. У генератора нет инструментов и побочных эффектов.
- Выход проверяется независимо от модели: ссылки ⊆ переданных, NLI по утверждениям, язык.
- Набор атак (документы с внедрёнными инструкциями на kk/ru/en) входит в e2e eval. Метрика — доля успешных атак до и после защиты.

## Отказ

- Ранний отказ без вызова LLM: калиброванная максимальная оценка reranker ниже τ. Экономит латентность, но риск ложных отказов на межъязыковых запросах выше.
- Отказ модели по промпту и SFT. Финальная политика — ADR-0008 после NLI.
- Оценка — precision/recall отказа на отвечаемой и неотвечаемой частях `qa` eval, по языкам и направлениям.

## Диагностика ответа по стадиям

Для каждого провального примера в режиме eval пишется трасса: ранги gold-пассажа в каждой ноге, после слияния, после reranker, наличие в промпте после обрезки, ответ, утверждения, вердикты. Затем стадия ошибки определяется первым «нет»:

| # | Вопрос | Стадия-виновник |
|---|---|---|
| 1 | Есть ли нужный факт в каком-либо чанке? | обработка документа, курация, чанкинг |
| 2 | Gold в top-`candidates_k` первой стадии? | retrieval |
| 3 | Gold в top-`context_k` после reranker? | reranker |
| 4 | Gold в промпте после бюджетной обрезки? | сборка контекста |
| 5 | Ответ верен при наличии gold в контексте? | генерация (не использовала доказательство) |
| 6 | Ссылки указывают на поддерживающий пассаж? | генерация (атрибуция) |
| 7 | Вердикт верификатора совпадает с человеческим? | verification |

Доли по стадиям считаются по языкам и направлениям. Инвестиция идёт в стадию с наибольшей долей, а не в ту, что легче менять. Вспомогательные метрики в духе RAGChecker:

- claim recall — доля фактов эталона в ответе;
- context precision — доля релевантных пассажей в контексте;
- context utilization — доля фактов из релевантного контекста, попавших в ответ;
- noise sensitivity — ошибки из-за нерелевантных пассажей;
- hallucination — утверждения без опоры в контексте.

## Латентность

Бюджет по стадиям — НФТ архитектуры §1, журнал — `latency_ms` в контракте. Рычаги:

- кеш эмбеддинга запроса;
- top-N reranker;
- параллельный поиск по двум коллекциям;
- стриминг токенов;
- батч NLI по всем утверждениям.

p95 меряется при целевой конкурентности, а не одиночными запросами.

## Оценка и ablation

- Метрики (`trifact-evaluation`): answer F1/EM для экстрактивных ответов, faithfulness по утверждениям, точность и полнота ссылок, refusal P/R, доля атак, p95.
- Ablation на одном тесте (архитектура §10): RAG без Extraction → + Extraction-сигналы → + дообученный Retrieval → + дообученный LLM → + Verification.

## Критерии готовности

- Пороги End-to-End гейта выполнены (`promotion.e2e_*`), корректность ссылок не ниже champion.
- Таблица стадий-виновников по языкам записана в MLflow `e2e`. Для крупнейшей категории есть гипотеза и эксперимент.
- Набор prompt-injection входит в e2e eval, доля успешных атак записана.
