# TriFact AI — проектные инструкции

Это главный документ правил работы над проектом. Он обязателен для любого агента и человека, который меняет репозиторий.

## 0. Перед любой работой

1. Прочитать [docs/PROGRESS.md](docs/PROGRESS.md): текущий этап, результаты, открытые вопросы, «что учесть дальше».
2. Прочитать раздел текущего этапа в [docs/ROADMAP.md](docs/ROADMAP.md): подшаги, артефакты, критерии готовности.
3. Если задача меняет архитектуру — сверить с [docs/architecture/docs/01-architecture.md](docs/architecture/docs/01-architecture.md) и ADR в [docs/architecture/adr/](docs/architecture/adr/).
4. Проанализировать и выбрать **следующий разумный шаг**. Не начинать работу, которая противоречит записям в PROGRESS, не обновив их.

## 1. Цель проекта

Мультиязычная (KK / RU / EN) ML-система, которая принимает документы любого вида, устойчиво извлекает из них сущности, ищет доказательства на всех трёх языках, отвечает на вопросы со ссылками на источники и проверяет свои утверждения.

Проект работает с данными масштаба **миллионов и десятков миллионов записей**. Каждое решение (формат хранения, алгоритм, модель, инфраструктура) выбирается с учётом этого масштаба, скорости и стоимости.

## 2. Протокол работы по этапам

- Проект разбит на **большие этапы** ([ROADMAP](docs/ROADMAP.md)); внутри каждого — подшаги.
- **Один рабочий шаг агента = один большой этап.** Этап выполняется целиком: проектирование → реализация → тесты → эксперименты → исправление ошибок → документация.
- Если этап нельзя закончить (нет доступа, нужен ресурс или решение пользователя), агент останавливается, записывает причину в PROGRESS и объясняет её в отчёте.

### Завершение этапа (обязательно, по порядку)

1. Все тесты этапа проходят; результаты экспериментов записаны (MLflow + таблицы в PROGRESS).
2. Удалён неактуальный код, временные файлы, мёртвые конфиги и эксперименты-однодневки.
3. Обновлены [docs/PROGRESS.md](docs/PROGRESS.md), затронутые разделы архитектуры, ADR (если решение изменилось).
4. Коммит(ы) в ветку `main` (см. §6).
5. Бэкап: `python scripts/backup.py --tag stage-NN`.
6. Подробный отчёт пользователю (шаблон — §9).

## 3. Чистота проекта (критично)

- **Никаких версионных копий файлов**: `*_v1`, `*_v2`, `final`, `new`, `old`, `copy`, «исправленный» и т.п. запрещены. История — в git, снимки — в бэкапах.
- Писать только код, который нужен для текущего этапа и будет использоваться. Без «на всякий случай», без закомментированных блоков, без неиспользуемых функций.
- Перед завершением этапа искать и удалять неиспользуемое: `ruff check --select F401,F841`, поиск мёртвых модулей и конфигов.
- Эксперименты оформляются как параметры одного скрипта (`params.yaml` / CLI / Hydra-override), а не как копии скрипта.
- Временные файлы — только во временных каталогах вне репозитория. Ноутбуки — только в `notebooks/`, без выводов в git (`nbstripout`), и только если они нужны для анализа.
- Сгенерированные данные, модели, отчёты-артефакты — не в git (DVC / MLflow).

## 4. Данные

- Хранилище — **data lake на Parquet** (zstd), шардирование ~1M строк / ≤512 MB на файл, партиции по `source/lang`.
- Обработка — потоковая и колоночная: Polars (lazy/streaming), DuckDB, PyArrow, datatrove для дедупликации и фильтров. `pandas` не используется для больших наборов. Никакой загрузки всего набора в RAM (15 GB на машине).
- Каждый источник имеет **манифест**: HF ID, revision (commit SHA), лицензия, дата загрузки, число строк, размер, хеш шардов.
- Слои: `raw → clean → curated → task` (NER / retrieval / SFT / NLI / eval). Слой `raw` никогда не меняется после загрузки.
- Сплиты строятся по исходному документу; тестовые наборы фиксируются до обучения и не меняются ([ADR-0007](docs/architecture/adr/0007-leakage-safe-splits.md)).
- Версионирование — DVC (remote: S3), отслеживаются каталоги шардов, а не миллионы мелких файлов.

## 5. Модели и эксперименты

- Каталог моделей с проверенными параметрами — [docs/research/models.md](docs/research/models.md); каталог данных — [docs/research/datasets.md](docs/research/datasets.md). Перед выбором модели — свериться с каталогом и обновить его, если появились новые факты.
- Каждый эксперимент — run в MLflow: git SHA, DVC-хеши данных, полный конфиг, метрики **по каждому языку**, время, железо.
- Сравнение всегда с baseline на одном и том же замороженном тесте. Улучшение без значимости (bootstrap CI / ≥3 сида для дешёвых моделей) не считается улучшением.
- Продвижение модели — только через гейт [ADR-0009](docs/architecture/adr/0009-model-registry-and-promotion-gate.md).
- Отрицательный результат — тоже результат: записывается в PROGRESS.

## 6. Git

- Работа только в ветке `main`.
- Коммиты атомарные, в формате Conventional Commits, заголовок ≤ 72 символов, настоящее время:
  `type(scope): описание` — `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `data`, `exp`, `chore`, `build`.
- Как минимум один коммит на завершённый этап; крупные подшаги — отдельными коммитами.
- Не коммитить секреты (`.env`), данные, веса, `__pycache__`, артефакты.
- Перед коммитом: `ruff check`, `ruff format --check`, `pytest -q`.

## 7. Бэкапы

- `python scripts/backup.py --tag <метка>` создаёт в `C:\Users\nurs\TrifactAI_backups\` полный `git bundle` (вся история) и архив неотслеживаемого рабочего состояния (`.env`, `.shrimp/`, локальные конфиги). Хранятся последние 30 снимков.
- Бэкап обязателен: после каждого этапа, перед массовыми удалениями или переписыванием, перед изменением схемы данных.
- Данные и модели бэкапятся через DVC remote (`dvc push`), а не этим скриптом.
- Восстановление: `git clone <bundle> TrifactAI` + распаковать архив состояния.

## 8. Код и инструменты

- Python 3.12, менеджер окружения `uv`, зависимости — в `pyproject.toml` (группы `serving`, `ingestion`, `ml`, `dev`).
- Линт и формат — `ruff`; типы — `mypy` для `src/trifact/core`; тесты — `pytest` в `tests/` (зеркально `src/`).
- Модули зависят от интерфейсов в `trifact.core.interfaces`, а не от конкретных моделей.
- Производительность измеряется, а не предполагается: для массовых операций (парсинг, эмбеддинги, индексация, дедуп) фиксировать throughput (записей/с) и пиковую память.
- MCP-инструменты проекта (`.mcp.json`):
  - **serena** — навигация и правки кода по символам;
  - **context7** — актуальная документация библиотек (перед использованием незнакомого API);
  - **exa** — поиск статей, бенчмарков, свежих релизов моделей;
  - **huggingface** — карточки моделей и датасетов, лицензии, размеры;
  - **mlflow** — чтение и сравнение экспериментов;
  - **structurizr** — валидация `workspace.dsl` и экспорт диаграмм после изменений архитектуры;
  - **shrimp** — декомпозиция этапа на подзадачи и их трекинг;
  - **playwright** — e2e-тесты web-интерфейса;
  - **github** — issues/PR, если подключён удалённый репозиторий.

```
(если остановлен)  — почему, что нужно от пользователя
```
