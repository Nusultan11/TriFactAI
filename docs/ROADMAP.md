# TriFact AI — дорожная карта

Один этап = один большой шаг работы ([AGENTS.md §2](../AGENTS.md)). У каждого этапа есть подшаги, артефакты и **критерии готовности**: этап не считается завершённым, пока все они не выполнены. Объёмы — из [research/datasets.md](research/datasets.md), модели — из [research/models.md](research/models.md).

| # | Этап | Главный результат |
|---|---|---|
| 0 | Фундамент проекта | Правила, документы, git, бэкапы |
| 1 | Data Platform & Acquisition | Все источники в data lake (Parquet), манифесты, DVC |
| 2 | Data Quality & Curation | Очищенные, дедуплицированные корпуса + отчёты качества |
| 3 | Task Datasets: gold, silver, synthetic | NER / retrieval / QA / NLI-наборы на миллионы примеров + замороженный eval |
| 4 | Document Processing Engine | Парсер любых документов с бенчмарком качества и скорости |
| 5 | Extraction | Champion NER + Entity Linking по трём языкам |
| 6 | Retrieval at Scale | Индекс 35 M чанков, champion embedder + reranker |
| 7 | Generation | Champion LLM для grounded QA на KK/RU/EN |
| 8 | Evidence Verification | Верификатор утверждений с откалиброванными порогами |
| 9 | System Integration & Serving | Рабочий онлайн-пайплайн, нагрузочные тесты, ablation |
| 10 | Product, Ops & Final Evaluation | Web, мониторинг, развёртывание, итоговый отчёт |

## Этап 0 — Фундамент проекта

1. Проектные инструкции (`AGENTS.md`, `CLAUDE.md`).
2. Каталоги моделей и данных с проверенными фактами.
3. Дорожная карта под масштаб миллионов записей.
4. Журнал прогресса `docs/PROGRESS.md`.
5. Скрипт бэкапа, git-репозиторий на `main`, первый коммит и снимок.

**Готово, когда:** все документы согласованы между собой, архитектура не противоречит дорожной карте, есть первый коммит и бэкап.

## Этап 1 — Data Platform & Acquisition

1. Окружение: `uv`-проект, lock-файл, `ruff`, `pytest`, pre-commit; инфраструктура `docker compose` (Postgres, Qdrant, Redis, S3, MLflow) поднимается и проходит healthcheck.
2. Структура data lake: `data/{raw,clean,curated,task,eval}/<source>/<lang>/part-*.parquet`, схема манифеста (`source.yaml`: HF ID, revision SHA, лицензия, строки, байты, хеши).
3. Универсальный загрузчик: потоковая загрузка HF → Parquet-шарды (zstd, ~1M строк), докачка после обрыва, параллелизм, проверка числа строк по метаданным.
4. Загрузка всех источников из каталога (Wikipedia ×3, FineWeb-2 kk, multidomain-kk, KazParC, KazNERD, WikiANN, WikiNEuRal, NEREL, SQuAD v2, SberQuAD, KazQAD, MS MARCO, mMARCO-ru, MIRACL, XNLI, ru-HNP).
5. Загрузка и потоковый парсинг Wikidata JSON dump → таблица `entities(qid, type, labels/aliases kk/ru/en, sitelinks)` без загрузки дампа в RAM.
6. Проверка лицензий; решение по каждому источнику — в манифесте.
7. DVC: remote S3, трекинг каталогов шардов, `dvc push`.
8. Отчёт: объёмы по источникам и языкам, throughput загрузки и парсинга.

**Готово, когда:** каждый источник в `raw` с манифестом, число строк совпадает с метаданными, `dvc status` чистый, тесты загрузчика проходят.

## Этап 2 — Data Quality & Curation

1. Нормализация (Unicode NFC, казахские буквы, гомоглифы латиница/кириллица, мусорные символы) — векторизованно на Polars, с тестами на крайние случаи.
2. Определение языка: lid.176 vs GlotLID на ручной выборке (особенно kk vs ky/tt/ru); выбор по F1, затем разметка всех документов и абзацев.
3. Фильтры качества (длина, доля букв, повторы строк/n-грамм, boilerplate) — пороги подбираются по ручной выборке, а не вслепую.
4. Дедупликация: точная (хеш) + MinHash-LSH (datatrove) внутри и между источниками; отчёт о доле дублей.
5. Контаминация: удаление из train-корпусов текстов, пересекающихся с будущими eval-наборами.
6. Статистика корпусов: распределения длины, языков, доменов; фертильность токенизаторов (XLM-R, Qwen3, Qwen3.5) на kk/ru/en.
7. Data cards по каждому curated-набору.

**Готово, когда:** curated-слой собран, отчёт качества показывает долю удалённого по каждой причине, ручная проверка выборки (≥ 500 документов на язык) подтверждает фильтры.

## Этап 3 — Task Datasets: gold, silver, synthetic

1. **NER:** приведение gold-наборов к общей схеме меток; silver NER из ссылок Wikipedia + типов Wikidata (цель 5–10 M предложений); оценка шума silver на gold.
2. **Retrieval:** пары из MS MARCO / mMARCO / MIRACL / ru-HNP; межъязыковые пары из KazParC; синтетические запросы к чанкам Wikipedia (учитель, цель 3–5 M) с фильтрацией round-trip retrieval; hard negatives.
3. **Grounded QA (SFT):** синтетика учителем Qwen3.5-35B-A3B на облачной GPU (vLLM): вопросы → ответы с `[chunk_id]`, межъязыковые варианты, неотвечаемые; фильтры (NLI-согласованность, ответ содержится в контексте, дубли); цель 1–2 M.
4. **NLI:** XNLI ru/en + перевод на kk с фильтрацией.
5. **Eval (замораживается здесь):** 30–50k примеров, все 9 языковых направлений, ≥ 3k проверены вручную; сплиты по исходному документу, проверка утечек.
6. Бюджет и стоимость облачной генерации фиксируются до запуска.

**Готово, когда:** все task-наборы в DVC с data cards, шум оценён, eval заморожен и захеширован.

## Этап 4 — Document Processing Engine

1. Тестовый корпус документов: PDF (текстовые, сканы, многоколоночные, таблицы), DOCX, HTML, TXT; kk/ru/en; с эталонной разметкой текста.
2. Двухуровневый парсер: быстрый путь (PyMuPDF) для простых PDF, Docling для сложной структуры; OCR-fallback (Docling OCR vs Tesseract `kaz+rus+eng` vs EasyOCR).
3. Метрики: CER/WER текста, точность порядка чтения, таблиц, заголовков; throughput (страниц/с).
4. Чанкинг: варианты (фиксированный, по предложениям, по секциям, разные размеры/перекрытия) — финальный выбор по метрикам retrieval в этапе 6.
5. Устойчивость: битые файлы, огромные документы, смешанные языки — без падений воркера.

**Готово, когда:** бенчмарк записан, выбран оптимальный путь для каждого типа документа, тесты на крайние случаи проходят.

## Этап 5 — Extraction

1. Baselines: GLiNER zero-shot, XLM-R base на gold.
2. Fine-tuning: XLM-R base/large на gold + silver (curriculum: silver → gold), HPO (Optuna), ≥ 3 сида.
3. Специализация kk: дообучение на KazNERD, сравнение единой и специализированной моделей; расширенные классы KazNERD.
4. DATE-экстрактор (regex + dateparser) и его оценка.
5. Оптимизация инференса: обрезка словаря, ONNX, int8; throughput на миллионах чанков.
6. Entity Linking: индекс меток Wikidata (миллионы), генерация кандидатов, ранжирование по контексту; accuracy@1 на ручной выборке.
7. Массовая разметка curated-корпуса champion-моделью.

**Готово, когда:** entity-level F1 по каждому языку и типу превосходит baseline с CI, champion в MLflow Registry, throughput замерен.

## Этап 6 — Retrieval at Scale

1. Индексация: пакетные эмбеддинги (облачная GPU для 35 M), Qdrant с on-disk векторами, сравнение квантизаций (none / int8 / binary + rescoring), MRL-размерности для Qwen3-Embedding.
2. Ступени масштаба 1 M → 10 M → 35 M: recall@k, nDCG@10, latency p50/p95, RAM, время индексации.
3. Сравнение эмбеддеров: BGE-M3, mE5-large(-instruct), Qwen3-Embedding-0.6B/4B.
4. Лексический поиск: BM25 sparse Qdrant vs sparse BGE-M3; гибрид RRF и взвешенное слияние.
5. Rerankers: bge-reranker-v2-m3, Qwen3-Reranker-0.6B/4B; подбор top-N по кривой качество/латентность.
6. Fine-tuning эмбеддера и reranker на парах этапа 3 (hard negatives, межъязыковые пары).
7. Анализ ошибок по 9 направлениям; выбор чанкинга по метрикам.

**Готово, когда:** champion-конфигурация не хуже предыдущей ни на одном направлении, кривые масштаба и бюджет памяти записаны.

## Этап 7 — Generation

1. Проверка поддержки Qwen3.5 в transformers / PEFT / llama.cpp / vLLM.
2. Baselines zero-shot с RAG: Qwen3.5-0.8B/2B/4B/9B, Qwen3-1.7B, KazLLM-8B, Sherkala-8B.
3. SFT: LoRA/QLoRA на grounded QA (миллионы примеров → отбор по качеству и разнообразию), подбор гиперпараметров, отказ при отсутствии доказательств.
4. Ablation состава данных (без межъязыковых, без неотвечаемых, только gold).
5. Квантизация для сервинга (GGUF Q4/Q5/Q8, AWQ) и её влияние на метрики.
6. Скорость: tokens/s, time-to-first-token, память на 4 GB и на GPU-сервере.

**Готово, когда:** дообученная модель обыгрывает baseline на faithfulness и answer F1 по всем языкам; если нет — это фиксируется и выбирается лучший baseline.

## Этап 8 — Evidence Verification

1. Разбиение ответа на утверждения (правила vs LLM).
2. NLI-модели: mDeBERTa-xnli, bge-m3-zeroshot, дообученная с kk-NLI.
3. Калибровка порогов, политика отказа, метрики (precision/recall вердиктов, ECE).
4. Скорость проверки на ответ.

**Готово, когда:** верификатор снижает долю неподтверждённых утверждений в ответах без значимой потери полноты.

## Этап 9 — System Integration & Serving

1. API (FastAPI), воркер (arq), Inference Service, LLM-сервер — полная реализация по архитектуре.
2. PostgreSQL-схема с миграциями (Alembic), массовая загрузка через COPY.
3. Батчинг и кеширование (эмбеддинги запросов, результаты reranker), стриминг ответа.
4. Нагрузочные тесты (k6 / Locust): RPS, p95, деградация при параллельной загрузке документов.
5. End-to-end eval и ablation study (без Extraction / с ним / с дообученным retrieval / с дообученным LLM).

**Готово, когда:** e2e-метрики и SLO из архитектуры §7 выполнены, ablation записан.

## Этап 10 — Product, Ops & Final Evaluation

1. Web (Next.js): загрузка, статусы, чат, цитаты, сущности; e2e-тесты Playwright.
2. Мониторинг: Prometheus-метрики, Grafana-дашборды «Service» и «Quality», алерты.
3. Развёртывание: Docker-образы, compose-профили, инструкция запуска с нуля.
4. Итоговый отчёт: все эксперименты, champion-модели, метрики по языкам, ограничения.

**Готово, когда:** система поднимается с нуля по инструкции, демо работает на реальных документах, итоговый отчёт опубликован.
