# 16. Разделение ответственности хранилищ

Date: 2026-11-18

## Status

Accepted

## Context

Если хранить корпус в PostgreSQL, нужны десятки миллионов чанков (~50 GB текста) и сотни миллионов упоминаний сущностей. Это перегрузит базу, которая обслуживает онлайн-запросы, и задублирует lake. С другой стороны, приложению нужны транзакционное состояние, журнал запросов и быстрый поиск кандидатов для Entity Linking.

## Decision

| Хранилище | Что хранит | Чего не хранит |
|---|---|---|
| **Data lake (Parquet)** | Источник истины для всех корпусов, чанков корпуса, аннотаций, векторов, task-наборов и eval | Состояние приложения |
| **PostgreSQL** | workspaces, documents, chunks и mentions пользовательских документов; queries, answers, claims, feedback; база сущностей `kb_entities` / `kb_aliases` (загружается COPY из lake) | Чанки и упоминания корпуса |
| **Qdrant** | Индексы поиска; payload = текст чанка + фильтры (ADR-0013) | Единственная копия каких-либо данных |
| **Object Storage (S3)** | Исходные файлы пользователей, DVC remote `local`, артефакты MLflow, GGUF | — |
| **Redis** | Очередь задач, кеш запросов | Долговременные данные |

Схема PostgreSQL меняется только миграциями Alembic. Массовая загрузка — через `COPY`.

## Consequences

Каждое хранилище можно восстановить. Qdrant перестраивается из lake и PostgreSQL, KB — из lake. Онлайн-база остаётся небольшой. Сущности корпуса доступны API через `entity_ids` в payload Qdrant и через KB, но список упоминаний по корпусу строится офлайн (DuckDB по `task/annotations`).
